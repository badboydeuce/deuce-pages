# 2026-09-17

## Feature request: admin pushes a number to the live user page (fill the empty box)
User wants: in portal `#results-user_page_X`, admin enters a number -> it appears in the visitor's page empty slot (e.g. `.match-empty` in a Deuce-branded "Verify it's you" page the user authored).

### Existing foundation (REUSE, do not rebuild)
- Session-command subsystem already built for admin->user push:
  - Admin endpoints: `POST /api/user-pages/:id/sessions/:sessionId/redirect` (setSessionCommand action=redirect), `DELETE /api/user-pages/:id/sessions/:sessionId/command` (action=clear). src/routes/userPages.js:345,383. Gated by `controlSessions`.
  - Storage: `setSessionCommand`/`deliverSessionCommand`/`getSessionCommand` in src/repositories/appRepository.js:2950+. Commands stored in `userPage.configs.sessionCommands[sessionId]`; shape = {action,targetUrl,targetFile,targetScreenId,targetRole,note,forceReload,status,createdAt,deliveredAt}. `deliverSessionCommand` ONLY delivers action==="redirect" && targetUrl and CONSUMES (deletes) it after delivery.
  - User-page poller: `checkSessionCommand` in script.js:3774 and deuce-runtime-client.js:242 polls `commandEndpoint` (`/session-command`) every 4s with userPageId+sessionId; applies `action==="redirect"` only.
  - Portal UI: `sessionCommandMarkup` (script.js:1961) renders the "One-click flow" panel (redirect buttons + Clear) inside active session cards (`activeSessionCardMarkup`).

### Key reality
- The user's example custom page does NOT include the DEUCE runtime client, so it does NOT poll session-command. For custom pages a lightweight "push receiver" snippet is required (generate sessionId, send heartbeat so it shows in portal active sessions, poll `/session-command`, write value into a target element).

### Proposed changes (NOT yet implemented)
1. appRepository `setSessionCommand`: support `action:"displayValue"`, store `value` + optional `target` (element id); sanitize + length-limit value.
2. `deliverSessionCommand`: also deliver `displayValue` and PERSIST (don't consume) — distinct from redirect which is one-shot.
3. New admin endpoint `POST /:id/sessions/:sessionId/command` accepting `{action:"displayValue",value,target?}` (same path as DELETE clear). Gate `controlSessions`.
4. Portal `sessionCommandMarkup`: add number input + "Push" button -> calls endpoint; show current value + clear.
5. Runtime client (deuce-runtime-client.js + script.js `checkSessionCommand`): handle `action==="displayValue"` -> write `value` into element `command.target` (id) or `[data-deuce-push-value]`; dispatch a DOM event for custom pages.
6. Provide standalone "push receiver" snippet for custom pages: generates sessionId, heartbeat, polls `/session-command`, writes value into target el. Needs userPageId (pass via data-attr/query) so admin can target the session.

### Gotcha
- sessionId must be shared: admin picks an active session in portal; the user page must poll with that same sessionId (and register it via heartbeat). Custom pages must send at least one heartbeat to appear as a targetable active session.

## IMPLEMENTED (2026-09-17) — per-screen `allowPushValue` flag, NOT global
User clarified scope: the toggle must live in **Imported screens / file mapping** (the same place as the "Redirect" checkbox) — i.e. a per-screen flag, not a per-page capability. Done:

Backend:
- `src/services/screenManifest.js`: added `allowPushValue` to normalized screen (default FALSE) and to `screenRevision` canonical.
- `src/repositories/appRepository.js`: `setSessionCommand` now stores `value` (sanitized, `<>` stripped, max 64) + `target` (id-safe regex, max 64) for `action:"displayValue"`; `deliverSessionCommand` ALSO delivers `displayValue` and PERSISTS it (does not consume, unlike redirect); `getSessionCommand` returns displayValue too.
- `src/routes/userPages.js`: NEW `POST /:id/sessions/:sessionId/command` (gated `controlSessions`, same path as DELETE clear) accepting `{action:"displayValue",value,target?}` -> setSessionCommand, returns `{userPage, command}`.

Portal:
- `script.js`: `sessionCommandMarkup` now computes `pageAllowsPush` from `page.packageManifest.screens` and renders a "Push to visitor" input+button (hidden unless the page has a screen with `allowPushValue`); push handler added after the clear handler. File-mapping UI got a "Push value" checkbox (`data-package-screen-push`) next to Redirect, read back on save, and passed through to runtime index mapping. `latestSessionCommand` + `commandStatusLabel` updated so a pushed value shows as "Value shown to visitor" / "Showing: X".
- `styles.css`: added `.session-push` / `.session-push-row` styling.

Visitor:
- `deuce-runtime-client.js`: `checkCommand` handles `action==="displayValue"` -> `applyPushedValue` writes into `command.target` (id) or `[data-deuce-push-value]`, dispatches `deuce:push-value` event.
- `push-receiver.js` (NEW, standalone snippet for custom pages like the Deuce example): embed `<script src="push-receiver.js" data-deuce-user-page="user_page_xxx">`, mark empty box with `data-deuce-push-value` (or id + target). It generates+persists a sessionId, sends `/api/traffic` heartbeats every 10s (so portal shows the session live + targetable), polls `/api/session-command` every 4s, writes value. Uses relative `/api/*` (worker rewrites to runtime API).

Verification: `node --check` passes on all edited files; unit tests pass (screenManifest 8, runtimeScreens 4, subscriptionCapabilities 3, redirectButtonsLayout 2, resultViewerCommandCenter 1, plus script.js portal tests 3) — 0 failures.
No DB-backed integration test added yet (setSessionCommand path needs a user page). Follow-up: optional integration test for the new endpoint + displayValue persistence.
